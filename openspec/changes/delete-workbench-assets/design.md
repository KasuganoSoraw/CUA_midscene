# Design

## Context

任务复核服务已经通过 catalog 将 builtin 与 user 任务解析为带 `writable` 的视图，录制 catalog 也只暴露录制根下已验证的一级目录。删除操作必须复用这些解析边界，不能把浏览器提交的名称直接转换成任意文件系统路径。参见 `proposal.md` 和 `specs/local-task-review-app/spec.md`。

## Goals / Non-Goals

**Goals:**

- 为用户任务和原始录制提供显式、可确认的删除操作。
- 将路径验证、只读保护和活动录制保护放在服务端，前端禁用状态只承担交互提示。
- 删除后让 catalog、当前选择和复核草稿立即收敛到磁盘现状。

**Non-Goals:**

- 不删除整个场景或自动移除空场景目录。
- 不删除历史 run、执行报告或从录制生成的任务。
- 不提供回收站、软删除或跨设备恢复能力。
- 不将删除能力暴露为 CUA Subagent Tool。

## Decisions

### 1. 删除服务解析现有 catalog 后再删除目录

任务删除先通过现有任务解析逻辑确认目标唯一存在且 `writable=true`，再验证目标位于 user projects root 的 `scene/task` 两级边界内。录制删除先通过录制 catalog 解析目标为配置根下一级目录。通过解析结果删除完整目录，可以覆盖任务或录制的全部关联资产，又不需要维护容易遗漏的文件清单。

直接接受绝对路径或仅依赖前端标识校验的方案会扩大攻击面，因此不采用。

### 2. 活动录制期间冻结原始录制删除

录制 Worker 处于 `arming`、`armed`、`starting`、`recording` 或 `stopping` 时，所有原始录制删除请求均被拒绝。该规则比只比较 `recordingId` 更保守，避免 Worker 尚未稳定报告目录名称时发生竞争。

### 3. 使用资源化 DELETE 接口和结构化成功结果

任务使用 `DELETE /api/tasks/:scene/:task`，录制使用 `DELETE /api/recordings/:recording`。成功响应返回被删除标识，前端据此刷新 catalog。不存在、只读和冲突目标通过现有结构化错误链路反馈。

### 4. 使用共享的应用内确认对话框

前端采用可复用的 Vue 确认对话框，支持标题、说明、目标名称、确认和取消文案。任务复核页只对已加载且可写的任务显示删除入口；录制详情页对已选录制显示删除入口。对话框不依赖浏览器原生 `confirm`，便于保持视觉一致性和中英双语。

### 5. 删除后由父级重新协调选择状态

任务删除成功后，父级重新加载 scenes/tasks 并清空已删除任务的 view、draft 与 steps，再按现有规则选择剩余任务。录制删除成功后，录制工作区重新加载 catalog，并由现有 `applyCatalog` 选择首个剩余项。这样避免单独维护第二套 catalog 状态。

## Risks / Trade-offs

- [目录递归删除不可恢复] → 对话框明确展示目标和不可恢复影响，服务端只接受已解析的单一资产目录。
- [删除与运行并发] → 当前版本不删除 run 产物；任务执行管理器持有执行输入后仍可完成。界面在任务运行活跃时禁用任务删除，并由服务端在后续实现中保留增加运行锁的空间。
- [Windows 文件占用导致删除失败] → 保留原始资产并返回文件系统错误，前端刷新前展示失败原因。
- [删除最后一个任务留下空场景] → 有意保留 `scene.json`，以便后续继续向同一场景创建任务。

## Migration Plan

新增接口和前端控件不改变现有读取、保存、运行及录制契约。部署后旧资产无需迁移；回滚代码不会影响尚未被用户显式删除的资产。
