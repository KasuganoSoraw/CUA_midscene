## Context

`startReviewServer()` 当前在未指定 `port` 时向 Fastify 传入 `0`，每次由系统分配不同端口。CLI 启动后 Fastify listener 会保持 Node 进程存活，但后续 `cua review` 不知道已有实例，因此会不断创建新进程。

review 服务必须区分相同程序但不同 `CUA_DATA_ROOT` 的实例，否则带 `--data-root` 启动的测试或其他项目可能错误复用现有页面。本轮只解决固定端口上的单实例复用，不承担完整服务生命周期管理。

## Goals / Non-Goals

**Goals:**

- 默认使用 `127.0.0.1:47831`。
- 相同 review 协议和相同数据根的服务已存在时复用 URL。
- 端口空闲时正常创建 Fastify 实例。
- 端口被不匹配服务占用时明确失败，不启动后续端口。
- 保留显式 `port`，尤其是 `port: 0` 的隔离测试能力。

**Non-Goals:**

- 不实现 `47832` 等候选端口递增。
- 不检测浏览器关闭，不自动停止旧进程。
- 不增加 daemon、PID 文件、服务列表、关闭 API 或 UI 按钮。
- 不改变 loopback、无 token 和现有 review 业务 API 的边界。

## Decisions

### 1. 默认固定端口，显式端口保持原语义

导出 `defaultReviewPort = 47831`。只有调用方没有传入 `options.port` 时才启用固定端口探测与复用；显式 `port: 0` 继续创建系统随机端口，其他显式端口直接尝试监听而不复用，便于测试和嵌入方管理自己的生命周期。

### 2. 使用受控身份接口识别可复用实例

Fastify 增加只读身份接口，返回固定服务名、协议版本和数据根指纹。指纹由规范化 `layout.data.root` 计算 SHA-256，不向浏览器暴露本地绝对路径。

启动方在默认端口请求该接口，只有服务名、协议版本和数据根指纹全部匹配时才判定为同一服务。不能只依赖 HTTP 200 或页面标题，避免复用其他本地程序。

### 3. 启动结果显式区分 created 与 reused

`StartedReviewServer` 增加 `reused` 状态，并允许复用结果不持有本进程创建的 Fastify instance。`close()` 对复用结果为 no-op，防止第二次 CLI 调用意外关闭第一个进程拥有的服务。

CLI 无论 created 或 reused 都保持输出 URL，并按既有 `--no-open` 规则决定是否调用系统浏览器。JSON 输出增加 `reused`，普通文本在复用时说明已打开现有服务。

### 4. 占用冲突只报错

若探测未匹配且监听返回 `EADDRINUSE`，错误消息明确指出 `47831` 已被其他程序或不同数据根服务占用。本轮不继续扫描端口，也不终止占用进程。

为处理“探测后、监听前”另一个同配置进程抢先启动的竞态，监听遇到 `EADDRINUSE` 后再探测一次；若此时匹配则返回 reused，否则报错。

## Risks / Trade-offs

- [已有旧版本随机端口服务不会被复用] → 新实现只管理固定端口；旧进程可由用户一次性清理，后续启动不再继续累积。
- [不同数据根不能同时使用默认端口] → 明确失败；需要并行隔离的调用方使用显式 `port: 0`。
- [身份接口增加一个本地只读 API] → 只返回常量和不可逆数据根指纹，继续仅监听 loopback。
- [固定端口被企业软件长期占用] → 本轮按用户要求不做递增，输出可理解错误并保留显式端口 API。

## Migration Plan

升级后首次 `cua review` 在 `47831` 启动；后续相同配置调用复用该实例。现有随机端口实例不会自动终止。回滚后服务恢复随机端口行为，不涉及任务数据迁移。

## Open Questions

无。端口递增和自动回收明确留待后续需求。
