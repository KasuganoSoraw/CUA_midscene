## Context

当前 review server 已经能够读取 canonical 场景与任务、编辑并保存任务，也能够启动独立的 Windows 录制器进程；实际任务执行则只由 `execution` 包的 CLI 暴露。用户若要验证刚复核的任务，仍需离开网页、手工拼接参数并从终端运行。

任务执行会独占并操作真实桌面，而且可能长时间没有标准输出。页面因此不能把执行当作一个普通同步 HTTP 请求，也不能用虚假的步骤百分比表达进度。首版同时要保持依赖边界简单，复用现有 runner 与 CLI，不把 Midscene 执行逻辑复制到 review server。

## Goals / Non-Goals

**Goals:**

- 在现有本地网页中提供独立、清晰的任务运行工作区，并支持从当前复核任务快捷进入。
- 从 canonical `task.json.inputs` 生成运行时输入表单，复用现有 `task run` 和 `act run` 语义。
- 以服务端持有的状态机管理准备倒计时和长时间运行，使页面刷新后仍可恢复观察。
- 通过现有 CLI 子进程隔离执行生命周期，并展示可靠的最终结果、错误摘要和运行目录。
- 不新增第三方运行时依赖。

**Non-Goals:**

- 不实现录制器和执行器之间的共享“桌面会话锁”；首版默认用户不会同时录制和运行任务。
- 不支持同时运行多个任务。
- 不提供完整实时日志流、伪造的步骤进度或持久化运行历史索引。
- 不新增全局快捷键；准备阶段使用页面可见的倒计时。
- 不执行尚未保存的浏览器草稿。

## Decisions

### 使用第三个工作台页签，并在复核页提供快捷入口

“任务运行”与“任务复核”“从录制创建任务”并列。运行页拥有自己的任务选择、输入和状态区域，避免执行状态与步骤编辑表单互相挤占；复核页仍提供“运行此任务”按钮，保留从编辑到验证的短路径。相比只在复核页塞入运行按钮，这一布局也允许用户单独选择其他已有任务运行。

### 只运行已保存的 canonical 任务

执行入口传递场景和任务标识，不把浏览器草稿作为临时任务发给后端。可写任务存在脏草稿时，“保存并运行”先完成现有保存流程，再切换运行页；只读内置任务可直接切换。这样执行器、CLI 和命令行用户始终读取相同的 source of truth，也避免新增临时任务协议。

### 由服务端管理准备倒计时

启动请求成功后，执行管理器进入 `preparing`，保存预计开始时间，并在五秒后启动子进程。用户可以在准备期切到目标窗口，页面也可以通过轮询展示剩余时间；浏览器刷新或离开页面不会取消计时。准备期停止会取消定时器并回到空闲状态。

相比等待新全局热键确认，倒计时无需额外底层输入依赖，也不会污染录制器的键盘钩子设计。

### 通过无 shell Node 子进程复用现有 CLI

review server 使用 `process.execPath` 启动现有 CLI，并以参数数组传递 `task run` / `act run`、场景、任务、数据目录和输入，不通过 shell 拼接命令。在源码开发环境中使用项目内 `tsx` 运行 `cli/main.ts`，构建交付环境优先运行 `dist/cli/main.js`。

这使执行继续沿用现有任务解析、输入校验、Midscene runner 和 run directory 契约。相比在 Fastify 路由中直接调用执行函数，子进程能隔离环境初始化、退出码和长生命周期故障，也与未来作为 Agent 子进程集成的方向一致。

### 使用单执行状态机而非长连接请求

进程管理器维护 `idle`、`preparing`、`running`、`stopping`、`succeeded`、`failed` 状态，并记录任务标识、模式、时间、运行目录、最终结果或错误摘要。同一时间只允许一个 `preparing`、`running` 或 `stopping` 会话；终态允许被下一次运行覆盖。

页面每秒轮询轻量状态 API。长时间没有 CLI 输出时仍准确显示“正在运行”和已用时间，而不是把请求超时误判为失败。首版不公开运行时输入值，避免状态查询无意回显可能敏感的内容。

### 以最终 JSON 与退出码共同判定结果

管理器限制性收集 stdout/stderr，在子进程退出后解析 CLI 最终 JSON。只有退出码为零且执行结果状态为成功时才进入 `succeeded`；否则进入 `failed` 并保留截断后的诊断。成功状态提取并展示 run directory，便于继续进入既有产物处理流程。

## Risks / Trade-offs

- [用户在倒计时结束前未切到正确初始界面] → 清楚显示五秒倒计时，并允许准备期取消后重新开始。
- [Midscene 长时间静默使用户误以为卡死] → 显示真实运行状态和已用时间，不承诺未知的步骤进度。
- [停止子进程可能留下不完整 run directory] → 将停止标记为失败/已停止并保留诊断；后续处理只消费成功结果。
- [review server 重启会丢失内存状态] → 首版接受该限制；运行产物仍由既有 run directory 持久化。
- [用户同时录制和执行导致桌面输入竞争] → 首版按用户决定不做跨模块锁，在界面文案中说明运行期间不要同时操作录制。
- [源码与构建产物的 CLI 路径不同] → 启动前显式探测受支持的两个入口，找不到时在准备阶段前返回可读错误。

## Migration Plan

1. 新增共享执行 API 类型、执行管理器和 Fastify 路由，不改变现有 review 与 recorder API。
2. 新增运行页与复核快捷入口，默认仍打开“任务复核”。
3. 通过服务与路由测试覆盖倒计时、并发拒绝、停止和结果解析，通过前端构建验证接口类型。
4. 回滚时移除新页签、路由和管理器即可；canonical 任务及已有运行目录格式不需要迁移。

## Open Questions

- 后续是否需要将录制、执行和其他桌面能力统一到可抢占或可排队的桌面会话协调器。
- 后续是否要基于 run directory 增加持久化历史列表及实时结构化步骤事件。
